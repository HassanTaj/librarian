## Evidence boundaries and current architecture assessment

- `lib/config.ts:43` lazily validates a complete environment/file configuration. It has no settings database lifecycle and does not cache configuration itself. Missing provider secrets prevent downstream runtime access.
- `lib/mongo.ts:34` retains a shared connection promise whose default initialization calls full `loadConfig()`; configuration and database bootstrap are coupled.
- `auth.ts:65` retains a runtime-auth promise/configuration. `createServerAuth` binds issuer/client/audience, secure database sessions, PKCE/state/nonce and encrypted account handling. Runtime settings cannot assume this singleton refreshes.
- `lib/sync/worker-startup.ts:27` loads full config once, then starts the worker with captured App credentials/content/approval settings; `instrumentation.ts` initiates it in Node runtime.
- Configuration consumers include `auth.ts`, `lib/mongo.ts`, worker startup, webhook intake, catalog create/update, admin/reader authorization, health and content/search/assets routes through Mongo/auth. These are all planning impact surfaces, not just the wizard UI.
- `lib/sync/webhook.ts` verifies HMAC over original bytes; the webhook route durably matches/admit jobs. GitHub clients use selected read-only installation tokens and bounded subtree/blob retrieval; worker jobs carry catalog revisions, leases and fenced immutable publication.
- `lib/auth/tokens.ts` already encrypts OAuth tokens using authenticated encryption and a host key. Preserve ciphertext compatibility and token-refresh/sign-in fences. It is not an instance-settings secret store.
- `lib/auth/admin.ts` grants catalog administration by current project `librarian-admin`; no separate instance-owner binding exists. Private reading uses a different role boundary and authorizes before generation/cache access.
- `lib/catalog.ts:19` reserves admin/api/auth/health/repositories, but accepts setup/settings. Future route registration therefore requires a real legacy collision check; no live catalog was inspected here.
- `.env.example`, Dockerfile, .dockerignore, package scripts and CI describe file-backed settings, non-root standalone packaging, existing provider fixtures and four-metric coverage. No production descriptors are added here. Existing v1 documentation records the actual sibling checkout as contabo; this invocation makes no live infrastructure assertion.
