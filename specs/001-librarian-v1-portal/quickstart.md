## Environment Configuration

Follow the [initial local DEV setup guide](../../docs/guides/initial-setup.md) for
provider-console steps, file-backed credentials, MongoDB user provisioning and SSH access.

`lib/config.ts` validates the `.env.example` server-side configuration contract lazily, with
file-backed secrets and sanitized errors; runtime routes and the worker use that configuration.
The tracked example contains placeholders only. Local secret files and content belong under ignored `.local/`,
and builds and CI fixtures must not require production values. CONTENT_ROOT must already exist
outside public; the encryption-key file uses canonical base64 for exactly32 random bytes.

The application uses the existing MongoDB deployment. `MONGODB_URI_FILE` must point to a file
containing the connection string for the dedicated `librarian` database and a least-privilege
application user; no MongoDB service is added to the application deployment. The MongoDB service
in GitHub Actions is disposable test infrastructure for database integration tests only. Production
secret files are mounted from scoped Swarm secrets and `CONTENT_ROOT` is set to the persistent volume.

GitHub Actions CI uses synthetic fixtures and no live provider credentials. The image-publish workflow
requires the GitHub Actions repository variable `REGISTRY_URL` to contain the registry host only (for
example, `gitea.perspective-v.com`); `REGISTRY_USERNAME` and `REGISTRY_PASSWORD` remain repository
secrets. Deployed application credentials are provisioned through scoped Swarm secrets, as required
by the project; they are never baked into a .env file, Docker build context or client-visible variable.

| Scoped data | Search/follow nested links, anchors and assets in equal-name repositories; publish while reading old g | Only selected authorized repo/generation; expired generation gives reload_required, not mixed fallback |
| Parser limits | Markdown/GFM plus allowlisted static Fumadocs MDX components; imports/exports, dynamic expressions, unknown components/attributes, HTML, YAML aliases/tags and encoded paths; limits-1/limit/limit+1 | Safe syntax passes; unsafe/over-limit candidates reject without execution or last-good loss |

## Separately Approved DEV and Production Handoff

This section is a future run guide, not authorization to provision/deploy now.

1. Inspect the actual infrastructure checkout/service state, Mongo version/topology/write durability,
   volume placement, GitHub permissions, Zitadel API audience/current-roles/refresh/logout, registry
   auth and DEV hostname. Follow infrastructure repository instructions; do not assume copied paths.
2. Prepare concrete scoped infrastructure changes and rollback, preserving previous image/config and
   consistent catalog/jobs/session/content backup. Obtain required owner approval before changes,
   credential provisioning, public-content or image publication.
3. Validate approved DEV login/current roles/expiry/logout, GitHub push/manual recovery, every protected
   path/browser cache, container workload, backup/restore and health/rollback. Keep live evidence separate
   from CI fixtures. Isolated recovery/rollback targets are each <=30 minutes for the acceptance corpus.
4. Only after all v1 completion gates and explicit production approval, use the established ssh contabo
   infrastructure workflow; verify health and browser behavior. Do not replace rollback with an
   unverified Compose command or fall back to an unguarded legacy private reader.
5. Record results in applicable feature tasks/checklists once those exist. Never mark an unrun live
   check complete or add a second state ledger.
