# Quickstart and Validation Guide: Librarian v1

**Status**: Planning guide; the v1 application/test commands below are planned interfaces.
The copied package currently has dev/build/start only and an empty static reader after removal of
unrelated documentation. Do not treat running that scaffold as a validated public/private portal.
**References**: [plan](plan.md), [data model](data-model.md), [HTTP contracts](contracts/http.md).

## Environment Configuration

The current scaffold does not read application environment variables; `.env.example` is the planned
server-side configuration contract until T003 implements and tests `lib/config.ts`. It contains
placeholders only. Local secret files and content belong under ignored `.local/`, and builds and CI
fixtures must not require production values.

The application uses the existing MongoDB deployment. `MONGODB_URI_FILE` must point to a file
containing the connection string for the dedicated `librarian` database and a least-privilege
application user; no MongoDB service is added to the application deployment. The MongoDB service
in GitHub Actions is disposable test infrastructure for database integration tests only. Production
secret files are mounted from scoped Swarm secrets and `CONTENT_ROOT` is set to the persistent volume.

GitHub Actions CI uses synthetic fixtures and no live provider credentials. The image-publish workflow
requires the GitHub Actions repository variable `REGISTRY_URL` to contain the registry host only (for
example, `gitea.perspective-v.com`); `REGISTRY_USERNAME` and `REGISTRY_PASSWORD` remain repository
secrets. Deployed application credentials are provisioned through scoped Swarm secrets, as required
by the project; they are never baked into a .env file, Docker build context or client-visible variable.

## Resource and Container Validation

Use the planned pinned standalone image, built outside the VPS. Test it locally at 0.5 CPU and
512 MiB with one replica, the real worker, persistent scratch volume and local dedicated Mongo.
Use the plan's three-catalog/500-page corpus, ten readers at 20 aggregate requests/s for 15 minutes,
including one ingestion, max-bound input tests, retention pressure and a restart.

Record image digest, corpus/count/bytes, latency p50/p95, cold reads, publication/ack times, process
RSS and container memory peak, CPU throttling, cache/index size, volume bytes, jobs/retry counts,
worker recovery time, browser coverage and error counts. No OOM/crash, correctness failure, privacy
failure, missing generation or exceeded finite bound is acceptable. Compare p95/cold/publication
targets and <=45 s recovery in the plan. Do not claim a bare healthy replica proves this workload.

Build inspection must prove legacy MDX/runtime/operations/state/images are absent from application
content and public artifacts. Only original reviewed branding is copied to public; snapshots/fixtures/
secrets are never in the image. Verify local-md/Shiki runtime files, selected highlighter languages,
the worker startup/build exclusion and no external repository dependency installation.

## Separately Approved DEV and Production Handoff

This section is a future run guide, not authorization to provision/deploy now.

1. Inspect the actual infrastructure checkout/service state, Mongo version/topology/write durability,
   volume placement, GitHub permissions, Zitadel API audience/current-roles/refresh/logout, registry
   auth and DEV hostname. Follow infrastructure repository instructions; do not assume copied paths.
2. Prepare concrete scoped infrastructure changes and rollback, preserving previous image/config and
   consistent catalog/jobs/session/content backup. Obtain required owner approval before changes,
   credential provisioning, public-content or image publication.
3. Validate approved DEV login/current roles/expiry/logout, GitHub push/manual recovery, every protected
   path/browser cache, container workload, backup/restore and health/rollback. Keep live evidence separate
   from CI fixtures. Isolated recovery/rollback targets are each <=30 minutes for the acceptance corpus.
4. Only after all v1 completion gates and explicit production approval, use the established ssh contabo
   infrastructure workflow; verify health and browser behavior. Do not replace rollback with an
   unverified Compose command or fall back to an unguarded legacy private reader.
5. Record results in applicable feature tasks/checklists once those exist. Never mark an unrun live
   check complete or add a second state ledger.

## Expected Evidence at Handoff

- Passing required tests, four global and four per-scope coverage metrics with explicit source inventory.
- Passing typecheck, lint and actual production build; no private content in static/public artifacts.
- Actual Mongo/FS fault and lease/restart proof; recorded live current-role and logout behavior.
- Measured budget/bounds/corpus/latency and consistent backup/restore/previous-version rollback.
- Owner approval references for public scope and approved infrastructure/publication/deployment.
